# WutheringWavesTool 多模块重构方案

> 生成时间：2026-08-11
> 决策依据：基于对 357 个 Java 源文件的完整结构调研、`com.kuro.*` 与 `cn.tealc.wutheringwavestool.*` 双包双向依赖分析、构建配置（pom/jlink/CI）、以及 `Setting.java` / `WebKujiequManager` / `BaseTask` 等关键文件的阅读。

---

## 一、当前架构问题（按严重程度排序）

### 🔴 问题 1：双根包 + 双向依赖（最致命）
`com.kuro.*`（122 类）和 `cn.tealc.wutheringwavestool.*`（218 类）是两套根包，却互相 import：
- `cn.tealc → com.kuro`：58 个文件引用
- `com.kuro → cn.tealc`：32 个文件引用

`com.kuro` 的类反而要用 `AppInjector`/`Config`/`ResponseBody`，`cn.tealc` 又要用 `com.kuro.kujiequ.model.sign.UserInfo`（被引 29 次）。这导致 `module-info.java` 里被迫写出 40+ 条 `exports`，还在 module 层面互相 `to` 放行。

### 🔴 问题 2：`thread/` 层 = 事实上的网络/数据访问层
50+ 个 `javafx.concurrent.Task` 子类承担了 HTTP 请求、JSON 解析、业务逻辑三重职责。`service/` 层很薄（多数 50~120 行），大量业务逻辑直接写在 `Task` 里，而 `Task` 又被 ViewModel 直接 `new` 出来调用。

### 🟠 问题 3：`Setting` 全局巨石 + 静态 `Config`
- `Setting.java`（634 行）用一个类装下**所有**配置项，UI 属性、游戏路径、签到、服务器账号、抽卡 ID 全混在一起，无分组无接口
- `Config` 是静态门面 + 静态 `ResourceBundle`，与 Guice 管理的 `Setting` 双轨并存
- 修改任意配置都要触碰这个上帝类

### 🟠 问题 4：根目录污染 + Git 跟踪了运行时产物
```
sqlite.db          ← 运行时数据库（557KB，已被 .gitignore 忽略）
settings.json      ← 运行时配置（已被忽略）
nul / lock         ← lock 被 git 跟踪，nul 是 Windows 重定向产物
data/ data3/ data4/ ← 多套用户数据目录并存
backup/ 游戏下载/    ← 运行/调试产物
libs/mvvmfx-1.9.0-SNAPSHOT.jar  ← 手动备份，未被 Maven 引用
```
`lock` 文件被 git 跟踪是隐患；`libs/` 里的 jar 是手动备份，pom 并未引用。

### 🟡 问题 5：MVVM 实施不彻底
- 43 View + 38 ViewModel，但 `MainView.java` 778 行、`OwnRoleDetailViewModel.java` 734 行，说明 View 里有大量本该拆分的逻辑
- `AppInjector.getInstance()` 在 ViewModel 里被直接静态调用，绕过了 DI，单测困难

### 🟡 问题 6：工具类杂乱
`util/` 里混着 `ImageTest`（测试代码误入主源码）、`AppLocked`（锁文件）、`GachaDataMigration`（数据迁移）、`NavLoader`（资源加载）—— 职责完全不相关。

### 🟡 问题 7：测试形同虚设
16 个测试文件全在 `src/test/java/test/` 下平铺，命名 `Main.java`/`SnapTest.java`，更像是手动调试脚本而非单元测试。

## 二、目标架构：3 个 Maven 模块 + JPMS 对齐

```
WutheringWavesTool/                       （parent pom，packaging=pom）
├── pom.xml                               父 pom，聚合 + 公共 dependencyManagement
├── wwt-core/                             基础层（HTTP、DI、配置、i18n、通知）
├── wwt-kuro-api/                         Kuro API 客户端层（原 com.kuro.* 122 个类）
└── wwt-app/                              应用主体（UI、DAO、service、thread、plugin、theme）
```

### 模块职责与依赖方向

```
wwt-app  ──depends on──▶  wwt-kuro-api  ──depends on──▶  wwt-core
   │                                                       ▲
   └─────────────depends on────────────────────────────────┘
```
- `wwt-core`：零内部依赖。放 `HttpUtil`、`ResponseBody`、`AppInjector`、`Config`、`Setting`、`NotificationManager`、`LanguageManager`、`AppConstants`
- `wwt-kuro-api`：依赖 `wwt-core`。放迁来的 `com.kuro.*`，包名统一为 `cn.tealc.api.kuro.{kujiequ,game,launcher,util}`
- `wwt-app`：依赖 `wwt-core` + `wwt-kuro-api`。放 UI、DAO、service、thread、plugin、theme、jna

## 三、关键解耦手段：依赖倒置切断 wwt-kuro-api → wwt-app 反向依赖

`com.kuro` 现有 29 处 `AppInjector.getInstance(HttpClient.class/ObjectMapper.class/DAO.class)` 反向调用 wwt-app。多模块化后 kuro-api 模块**不能**再依赖 app 模块。解法：

1. `wwt-core` 定义抽象：`HttpClientProvider`、`ObjectMapperProvider`、`KuroConfigSource`（读 devCode/serverId 等）接口
2. `wwt-kuro-api` 通过构造器注入这些接口（`BaseTask` 不再静态拉 `AppInjector`）
3. `wwt-app` 的 `AppModule`（Guice）提供这些接口的实现，把 `HttpClient`/`ObjectMapper` 实例传进去
4. `ResponseBody`/`ResponseBodyForApi`/`SourceType` 下移到 `wwt-core`（它们是纯 DTO，无内部依赖）
5. `ApiUtil` 里的 `AppConstants.API_DECRYPT_KEY` 改为通过 `KuroConfigSource` 接口获取；`Config.setting()` 的引用点一并改走接口
6. `SignService`（在 app 模块）→ `kuro-api` 的依赖：保留方向（app → kuro-api，合法）。`SignTask` 里 `AppInjector.getInstance(SignService.class)` 反向调用，改为**事件回调**：kuro-api 定义 `SignCallback` 接口，app 实现并注入
7. `GameRoleDataSaveTask` 等 Task 直接用 `GameRoleDataDao`：这些"Task 写本地 DB"的设计本身有问题。把 DB 写入职责上移到 app 的 service 层，kuro-api 的 Task 只返回数据，不碰 DAO

### 阶段 1：拆分 Setting 上帝类（1 周，独立提交）

**目标**：把 634 行 `Setting.java` 按 8 个注释分段拆为分组配置类。

**现状**（`Setting.java` 字段分组，按行号）：
- 设置-首选（游戏路径相关，45–51 行）
- 设置-基础设置（UI/主题/背景，52–67 行）
- 设置-游戏行为（68–72 行）
- 设置-其他设置（73–77 行）
- 高级启动相关（81–84 行）
- 抽卡分析相关（85–92 行）
- 签到相关（93–96 行）
- 服务器相关（98–100 行）
- 顶部 UI 字段（29–44 行：devModel/language/appWidth/...）

**拆分方案**：
```
wwt-app/src/main/java/cn/tealc/wutheringwavestool/base/config/
├── Setting.java          （保留，但变为聚合容器：@JsonUnwrapped 或 @JsonProperty 把子配置组合）
├── UiSetting.java        （UI 字段：language/theme/appWidth/uiScale/leftBarShow/diyHomeBg*）
├── GameSetting.java     （gameRootDir/gameStarAppPath/gameOfficialLauncherDir + 游戏行为字段）
├── LauncherSetting.java  （userAdvanceGameSettings/appParams/startUpParams）
├── GachaSetting.java     （gachaCurrentPlayerId/gachaListModel）
├── SignSetting.java      （autoKujieQuSign/lastKujiequSignTime）
├── ServerSetting.java    （serverUsername/serverPassword）
├── AppBehaviorSetting.java （devModel/support/skipVersion/checkNewVersion/autoStart/silentStart/closeEvent/resourceSource/exitWhenGameOver/hideWhenGameStart/autoStartGame/useLocalCacheUser/noKuJieQu/homeViewIcon/homeViewRole/logLevel）
```

- 保留 `Setting.java` 作为**聚合 + 序列化入口**，旧字段以 `@Delegate`（Lombok）或手写 delegate 转发，保证**二进制兼容**——所有现有引用 `setting.gameRootDirProperty()` 的代码不动
- `Config.setting()` 静态门面保留，内部委托给分组类
- 把 `Setting.java` 的 2 个内部 `ObservableListSerializer`/`ObservableListDeserializer` 抽到 `base/config/serializer/` 独立类
- 提交：`refactor: 拆分 Setting 上帝类为分组配置`

## 五、风险与缓解

| 风险 | 缓解 |
|---|---|
| Guice 跨模块绑定失效 | `AppModule` 集中在 wwt-app 注册所有绑定；kuro-api 不直接拿 `AppInjector`，改构造注入 |
| mvvmfx 的 FXML 反射找不到 ViewModel 类 | wwt-app 的 `module-info` 对 mvvmfx/fxml 用 `opens` 而非 `exports` |
| `com.kuro.kujiequ.model.sign.UserInfo` 被 wwt-app 引用 29 次，包名改动多 | IDE 批量重构 + `sed` 校验；改动是机械的，逻辑零风险 |
| jlink 模块路径断裂 | jlink 当前不在 `mvn package` 路径上，只影响 `javafx:jlink` 手动目标，本次不破坏 |
| 阶段中间编译失败 | 每阶段独立提交，编译失败就 `git revert` 单阶段重来 |

## 九、调研依据摘要（供审查时回溯）

- `com.kuro.*` 122 个类，是 **in-repo 源码**（不是外部 Maven 依赖），分布在 `com.kuro.{game,kujiequ,launcher,util}`
- `com.kuro → cn.tealc` 反向依赖 32 文件，集中在：`AppInjector.getInstance()`（29 处，拿 HttpClient/ObjectMapper/DAO/SignService）、`ResponseBody`（34 处）、`Config`/`AppConstants`（4 处）
- `cn.tealc → com.kuro` 正向依赖 58 文件，最热：`UserInfo`（29 处）、`Role`、各 `Task` 子类
- `com.kuro.util.HttpRequestUtil` 是底层 HTTP 工具，被 `SignService`（cn.tealc）也引用——这是反向上行依赖
- `WebKujiequManager`（330 行桥梁）只引用 `com.kuro.kujiequ.model.sign.UserInfo` 一个类，不实例化 com.kuro Task，耦合面小
- 构建是 `maven-shade-plugin` fat jar（mainClass=`cn.tealc.wutheringwavestool.Launcher`），`javafx:jlink` 不在 `mvn package` 路径上，多模块化约束主要是 Maven 依赖图
- `lock` 文件被 git 跟踪（运行时锁文件误入仓库）；`libs/mvvmfx-1.9.0-SNAPSHOT.jar` 未被 pom 引用（手动备份）
- `Setting.java` 有清晰的注释分段，是天然拆分边界
- `dao/JdbcUtils`（app 的 sqlite.db）与 `dao/GameJdbcUtils`（游戏自带 DB）职责不同，均在使用，非冗余
